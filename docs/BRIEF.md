# Project brief: JudgeCal, an LLM-as-judge calibration toolkit

## Role
You are my senior pair-programmer and technical lead on this project. Before writing code, read this brief, then ask me at most 3 clarifying questions. Build in small, tested increments and explain key design decisions briefly. I'm an AI engineer in training and want to learn from this, so prefer clear, idiomatic code over clever code.

## Problem
Teams use an LLM as a judge (a model that scores or ranks other models' outputs) in eval pipelines, CI gates, and leaderboards. Almost nobody measures how reliable the judge is. Known failure modes:
- **Position bias:** in pairwise comparisons the judge favors the first or second answer regardless of quality.
- **Length/verbosity bias:** longer answers get higher scores regardless of quality.
- **Self-preference bias:** a judge rates outputs from its own model family higher.
- **Inconsistency:** the same input gets different scores across runs, temperatures, or prompt phrasings.
- **Low agreement with humans** on some criteria (e.g. factuality) even when it is fine on others (e.g. fluency).

## What already exists (do not rebuild these)
General eval frameworks (Ragas, DeepEval, Promptfoo, LangSmith evals, OpenAI Evals) and research (MT-Bench / Chatbot Arena "LLM-as-a-judge" paper, JudgeBench, RewardBench, AlpacaEval length-controlled win rates). They mostly *use* a judge. They rarely *audit* the judge per metric and produce an actionable reliability score.

## What this project adds
1. **Human-agreement measurement:** compare judge outputs to human labels, per metric and per judge.
2. **Bias detectors:** position, length, and self-preference, each with an effect size and confidence interval.
3. **Consistency measurement:** repeat runs, vary temperature and prompt wording.
4. **Trust score per (judge, metric):** a single interpretable 0-100 score plus the breakdown, with a recommendation such as "safe to use", "use with position-swapping", or "do not use for this metric".
5. **CI-friendly CLI and report:** a judge audit that can run in GitHub Actions and fail if a judge's trust score drops below a threshold.

## Scope (v1)
- Pairwise comparison and single-answer scoring (1-5 or 1-10) modes.
- Judge providers behind one adapter interface: Anthropic, OpenAI, and one self-hosted or small open model (via an OpenAI-compatible endpoint, e.g. SGLang or vLLM).
- Public datasets with human labels as the default benchmark. Verify exact dataset names, licenses, and formats online before using them. Candidates: MT-Bench human judgments, Chatbot Arena pairwise data, HelpSteer, SummEval, JudgeBench, RewardBench.
- Users can bring their own labeled CSV or JSONL.

Out of scope for v1: training judge models, a hosted SaaS, a multi-user auth system.

## Methodology (design these carefully)
- **Agreement:** accuracy for pairwise; Cohen's kappa for categorical; Krippendorff's alpha or weighted kappa for ordinal; Spearman or Kendall tau for rank correlation. Always report bootstrap confidence intervals.
- **Position bias:** run each pairwise item in both orders (A,B) and (B,A). Report the flip rate (verdict changes when order swaps) and the first-position win rate against the 50% null. Use a binomial or permutation test.
- **Length bias:** measure the correlation between length difference and judge preference. Then, controlling for human quality labels, fit a regression (e.g. logistic for pairwise) to isolate the length effect. Report a length-controlled agreement score.
- **Self-preference:** needs outputs generated by known models. Compare how the judge rates its own family's outputs versus others at matched human-rated quality. Report the effect size and CI. Flag clearly when the data can't support this test.
- **Consistency:** repeat the same item N times (e.g. 5), at temperature 0 and at a higher temperature, plus 2-3 paraphrased judge prompts. Report score variance and verdict stability.
- **Trust score:** a transparent weighted combination of agreement, bias penalties, and consistency, with the weights configurable and documented. Do not hide the components. Show uncertainty (CI) on the final score. Explain in the README why the weights were chosen, and be honest about their limits.
- **Statistical care:** sample sizes can be small, so warn when a result is underpowered rather than over-claiming.

## Tech stack (use what fits, don't force everything)
- **Core:** Python 3.11+, pydantic, pandas/numpy, scipy/statsmodels, scikit-learn, pytest, typer (CLI), async API calls with retry and rate limiting.
- **Experiment tracking:** MLflow (primary). Log every audit run's params, metrics, and report artifacts. Weights & Biases is optional.
- **Tracing/cost:** Langfuse for judge call traces, token cost, and latency per judge.
- **Data versioning:** DVC for benchmark datasets and cached judge outputs (caching also saves API cost).
- **Serving/UI:** FastAPI for an optional API; Streamlit (or similar) dashboard for reports.
- **Packaging and CI/CD:** Docker, GitHub Actions (tests, lint, a scheduled audit run, and a trust-score gate).
- **Cloud (stretch):** Terraform plus AWS (S3 for datasets and reports, Lambda or ECS for scheduled audits), or GCP Vertex equivalents. A self-hosted small judge served with SGLang on a GPU cloud instance.

## Milestones (propose adjustments)
1. **Foundation:** project skeleton, data schema, one dataset loader, one judge adapter, caching, and tests.
2. **Agreement and consistency metrics** with bootstrap CIs, validated on synthetic data with known ground truth.
3. **Bias detectors** (position, length, then self-preference), each with a synthetic test that plants a known bias and checks that it is detected.
4. **Trust score and report** (markdown/HTML plus plots).
5. **Tracking and tracing:** MLflow, Langfuse, DVC integration.
6. **CLI + GitHub Actions gate**, Docker image.
7. **Dashboard, and a case study:** audit at least 3 judges on at least 2 metrics and publish findings in the README.
8. **Stretch:** Terraform/AWS scheduled audits, SGLang-served small judge.

## Working rules
- Start by confirming the plan and proposing the first milestone's task list. Don't write the whole project at once.
- Use test-driven development for the metrics. Statistical code must have tests with known answers.
- Never hardcode API keys. Use environment variables and a `.env.example`.
- Keep API cost low: cache judge outputs, support a `--limit` flag for sample runs, and show estimated cost before big runs.
- When uncertain about a dataset's license or format, or a library's current API, check the official docs first rather than guessing.
- After each milestone, summarize what was built, how to run it, and what to do next.
